## 실행 결정

**이 PR은 자료 조사와 학습 계약을 검증 가능한 상태로 마무리한다.** 연구가 끝나기도 전에 세 덱을 동시에 구현하거나 현재의
`Backlog` 위치에 빈 교본/Playground를 만들지 않는다. 구현 착수 시 대상 덱을 repository의 active 위치로 이동하고,
독립적으로 검토 가능한 최소 학습 단위만 작성한다. 다른 storage 또는 Notion으로 복제·동기화하지 않는다.

최종 목표는 Rust 자체를 전부 학습하는 것이 아니라 다음 질문에 실제 증거로 답하는 것이다.

1. Python 사용자가 Rust ownership·오류 처리·컴파일러 피드백을 이해하고 작은 crate를 개발할 수 있는가?
2. Rust 라이브러리의 성능을 추측이 아닌 정확성 보존·profiling·반복 측정으로 평가할 수 있는가?
3. Python API와 오류 계약을 유지하는 Rust 구현을 패키징하고, end-to-end 비용과 agentic coding 비용을 별도로 평가할 수
   있는가?

## R1: 첫 실제 제작 단위의 정의

- 학습 전제: Python 함수 호출·값 참조·예외·단위 테스트는 이해하며 Rust 문법을 처음 접한다.
- 목표 역량: `cargo`가 무엇을 빌드/검증하는지 설명하고, `String`의 move와 `&str`/참조의 borrowing이 호출자·피호출자에게
  미치는 차이를 **컴파일 전에 예측**한다.
- 설명 흐름: Python 이름과 객체 → Rust 값과 소유자 → move 후 이름의 유효성 → 공유 차용 → compiler 진단 → 테스트.
- 첫 실습: 표준 라이브러리만 사용하는 작은 `lib` crate. owned `String`을 받아들이는 함수와 borrowed 문자열을 읽는 함수를
  비교하고, 반례를 예측·수정한다.
- 과제: 실패 컴파일 예시의 결과 예측, 최소 수정과 이유 설명, 같은 결과를 내는 API 두 가지의 trade-off 비교, 정상/경계값
  테스트를 추가한다.
- 검증: compile-fail 예시는 의도적으로 기본 빌드 경로 밖의 교본 예제로 유지한다. 실습 crate는 기본 검사에서 성공해야
  한다. 실행 결과를 얻기 전에는 통과했다고 쓰지 않는다.
- 제외: Python FFI, `unsafe`, async runtime, 다중 플랫폼 빌드, 성능 우열 주장.
- 착수 조건: 본 PR의 문서 설계와 CI를 검토한 뒤 **별도 변경**으로 착수한다. Backlog에서 active 이동 시 기존 디렉터리를
  복사하지 않는다.

## R3의 실증을 위해 지금부터 보존할 질문

**정확성 계약:** Python에서 관측되는 값, 순서, Unicode, 오류 종류·시점이 바뀌면 Rust core의 단위 테스트가 성공해도
Python 통합 테스트는 실패로 판정한다. 공통 입력 계약은 실제 구현 전에 경계값과 허용/거부 입력을 결정한다.

**성능:** baseline Python과 Rust-only 측정만으로 Python 사용자에게 이득이 있다고 결론내리지 않는다. 동일 workload,
최적화된 배포 빌드, 작은 입력/다회 호출/배치 입력, 반복 횟수와 노이즈를 비교한다. 빠르지 않으면 Python 구현을 남기는
결정도 합격이다.

**Agentic coding:** 모델·프롬프트·과제 난도·테스트 예산·환경을 기록하고, 코드 실행 시간과 구현/컴파일/재시도/인간 리뷰에
걸린 전체 시간을 따로 계산한다. 컴파일 성공만으로 정확성을 인정하지 않는다.

## 리뷰 → 개선 운영

각 실질적 변경에는 `Research → Plan → Work → Review`를 적용한다. 리뷰가 구현 오류나 학습 계약의 결함을 찾으면 가장 작은
해당 단계로 돌아가서 고친 뒤 동일 기준으로 재검토한다. 기계적인 포맷 수정이나 근거 없는 재검토를 반복 횟수로 세지
않는다.

**Review 1 — 근거·범위:** 공식 자료가 실제 주장을 지지하는가? 현재 릴리스와 교본 API가 일치하는가? 세 덱의 책임이
섞이거나 prerequisite가 누락되지 않았는가?

**Review 2 — 사용 가능성:** 다음 작업자가 첫 commit의 수정 파일, 예제의 동작/실패 계약, 테스트·교본 완료 조건, 실제로
하지 않은 검증을 구분할 수 있는가?

**Review 3 — PR 통합:** CI 결과와 GitHub의 실제 PR head를 확인한다. `.inbox/`의 임시 자료가 저장소의 canonical
policy처럼 인용되거나 Notion state 변경으로 잘못 이어지지 않았는가? 비밀·사적 데이터·복제 제한 자료가 없는가?

리뷰 발견사항은 **수정/이월/범위 밖**으로 분류한다. 범위 밖은 근거 없이 현재 PR에 추가하지 않는다. 각 재검토에서는
해결된 항목과 아직 검증하지 못한 항목을 다시 확인한다.
