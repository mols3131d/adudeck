# 0장 · 소개

주문 처리가 느려졌다고 하자. 전체 소요 시간만으로는 장바구니 검증이 오래 걸렸는지, 결제가 오래 걸렸는지
구분하기 어렵다. 각 작업의 시작과 끝을 관찰하고, 같은 주문 처리에 속한 작업을 연결해야 원인을 좁힐 수 있다.
이 덱은 그 근거를 어떻게 만들고 읽는지부터 시작한다.

## 무엇을 배우는가

실행 중인 시스템이 자신의 동작을 설명하기 위해 내보내는 데이터를 텔레메트리(telemetry)라고 부른다.
이번 덱에서는 먼저 한 작업의 실행을 기록하는 스팬(span)과, 관련 스팬을 연결하는 트레이스(trace)를 다룬다.
이후에는 반복 실행에서 횟수나 분포 같은 상태를 관찰하는 메트릭(metric)을 다룬다.

예를 들어 주문 처리 한 번에서 검증과 결제가 실행됐다면, 트레이스를 통해 그 작업 사이의 관계를 조사할 수 있다.
여러 주문 처리의 소요 시간 분포를 보고 싶다면 개별 트레이스만 읽기보다 메트릭으로 관찰하는 편이 질문에 맞는다.
둘은 같은 시스템을 보더라도 답하려는 질문과 데이터의 형태가 다르다.

OpenTelemetry는 이런 텔레메트리를 만들고 수집·전송하는 데 사용하는 API, SDK와 도구를 제공한다.
데이터를 생성하는 것, 다른 프로세스로 보내는 것, 저장된 데이터를 검색하고 화면에서 해석하는 것은 각각 다른 책임이다.
처음에는 콘솔에 출력해 생성된 데이터를 직접 읽는다. 이후 서비스와 전송 경계를 추가하면서 어디서 관계가 이어지고
어디서 데이터가 끊겼는지 관찰한다.

## 학습하는 방식

이 덱에서는 실행 전에 예상되는 관계를 적고, 실행 후 실제 근거와 대조한다.
명령이 성공했다는 것만으로 텔레메트리의 의미를 이해했다고 판단하지 않는다.

첫 실습은 다음 세 작업을 다룬다.

```text
checkout
├─ validate_cart
└─ charge_payment
```

세 작업의 이름을 아는 것만으로는 같은 주문 처리에 속하는지 확정할 수 없다.
[첫 트레이스](../02-first-trace/README.md)에서 식별자와 부모 관계를 읽고, 호출 하나의 현재 컨텍스트를 바꿔 연결이
달라지는지 확인한다. 정확한 식별자 값을 암기하는 대신 관계가 만들어지는 이유를 설명하는 것이 목표다.

## 시작 전 점검

Python 함수와 `with` 블록을 읽고, 터미널에서 프로그램을 실행할 수 있으면 시작할 수 있다.
후속 서비스 실습에서는 프로세스, 환경 변수, HTTP 요청과 응답의 기본 개념이 필요하다.
백엔드 운영 경험은 필요하지 않다.

다음 두 질문에 답해 보자.

1. 주문 처리 한 번의 내부 작업 관계와 여러 주문 처리의 소요 시간 분포는 각각 어떤 근거가 필요한가?
2. 콘솔에 스팬이 보이는 것만으로 다른 프로세스로의 전송이나 백엔드 저장까지 확인했다고 할 수 있는가?

점검 기준은 질문에 맞는 데이터를 구분하고, 관찰한 경계까지만 결론을 내리는 것이다.
이제 [환경 준비](../01-setup/README.md)에서 첫 실습 환경을 준비한다.
